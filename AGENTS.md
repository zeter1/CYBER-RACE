# AGENTS.md - CYBER RACE: CAR WARS

Отвечайте пользователю по-русски, простыми словами. Это статическая браузерная игра на Three.js; entrypoint - `index.html`. Меняйте только файлы согласованной задачи, сохраняйте чужие изменения.

## Быстрый вход

1. Прочитайте [README.md](README.md): назначение, запуск, управление.
2. Найдите задачу в [карте кода](docs/CODE_MAP.md); читайте указанный owner, его вызовы и ближайшие проверки.
3. При изменении границы модуля проверьте [архитектуру](docs/ARCHITECTURE.md); порядок работы и рецепты расширения - в [DEVELOPMENT.md](docs/DEVELOPMENT.md).
4. Выберите проверки по [VERIFICATION.md](docs/VERIFICATION.md). Фактический автоматический набор задаёт [CI](.github/workflows/validate.yml).

Не перечитывайте весь `runtime.js` для небольшой задачи: карта содержит имена функций для точечного поиска. Не создавайте второй документ с тем же назначением.

## Границы изменений

- Обычные `<script>` подключаются в установленном порядке и регистрируют API в `globalThis.CyberRace`. Новая зависимость требует согласованных изменений подключения и structural validator. Не переводите проект на сборщик или другой способ загрузки ради небольшой задачи.
- Чистые функции AI, баллистики, гонки и HUD принимают данные; DOM, Three.js, звук, таймеры и применение урона остаются у browser/runtime владельцев. Не возвращайте вынесенные вычисления в `runtime.js`.
- Баланс меняйте только в рамках задачи на игровой процесс. Значения есть не только в `config.js`, но и в difficulty, runtime и simulation-функциях. Рефакторинг должен сохранять поведение.
- Порядок обновления кадра, проверки доступности ввода и переходы меню являются контрактами. Не исправляйте их добавлением случайных задержек или снятием существующих защит.
- При изменении моделей сохраняйте контракт машины и владение общими geometry/material/texture из архитектуры. Удаление экземпляра бонуса не должно освобождать общие ресурсы фабрики.
- Не очищайте пользовательский `localStorage` и не меняйте его ключи ради проверки. Используйте отдельный тестовый browser context; состояние и его владельцы описаны в архитектуре.
- Детерминированный fixture - ожидаемый результат, а не способ скрыть регрессию. Меняйте его только при объяснённом изменении поведения и независимой проверке новых ожиданий.

## Работа и доказательства

До исправления бага разделите цель, наблюдаемые факты, гипотезу и предлагаемое изменение. Найдите этап сбоя и проверку, отличающую гипотезы. Обратимые решения внутри задачи принимайте самостоятельно.

До выполнения кода проследите import/startup и достижимые записи, сеть и browser state. Текущие Node contracts работают с синтетическими данными; browser startup читает настройки, а игровые действия могут сохранить рекорды. После изменения выполняйте достаточные проверки по затронутой границе, без повторов ради случайного зелёного результата.

Проверка синтаксиса, contracts, replay и boot marker доказывают разные вещи. `data-cyber-boot="ready"` не доказывает управление, звук, внешний вид, баланс или FPS. Первый сбой сохраняйте в отчёте; при неизвестной причине укажите UNKNOWN и следующий точный check.

## Документация и завершение

- README описывает текущую игру и запуск; CODE_MAP - поиск кода; ARCHITECTURE - контракты; DEVELOPMENT - порядок доработки; VERIFICATION - процедуры и границы проверок.
- Обновляйте только затронутых владельцев документации. Для публичных возможностей и запуска синхронизируйте русский и английский README.
- Записывайте принятую задачу одним блоком в [CHANGELOG.md](CHANGELOG.md) с фактическим локальным временем и числовым UTC offset. Сохраняйте предыдущую историю; правка документации сама по себе не требует новой версии.
- В финале кратко укажите результат, изменённые файлы, выполненные проверки, VERIFIED / NOT_VERIFIED и оставшийся ручной сценарий. Не объявляйте gameplay проверенным по одному запуску или headless boot.
