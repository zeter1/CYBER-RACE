# Руководство по доработке игры

Используйте [карту кода](CODE_MAP.md) для поиска, [архитектуру](ARCHITECTURE.md) для контрактов и [проверки](VERIFICATION.md) для команд и ручных сценариев. Документ описывает рабочий порядок для человека и coding agent; он не добавляет новый игровой API.

## Среда разработки

Это набор HTML и JavaScript без `package.json`, npm-зависимостей и этапа сборки. Для игры нужен браузер с WebGL. Three.js 0.160.0 включён локально в `vendor/three/three.module.js`; CDN используются только как резервные источники, если локальный модуль недоступен. Локальный сервер и адрес запуска описаны в [README](../README.md#запуск).

Node.js нужен для локальных проверок; CI использует Node.js 24. Python нужен только для показанного HTTP-сервера. `rg` удобен для поиска, но не требуется игре. Команды запускайте из корня, содержащего `index.html`, `src`, `tests` и `scripts`; в PowerShell используйте `Set-Location -LiteralPath 'путь к папке игры'` со своим фактическим путём.

Для gameplay-проверок используйте отдельный тестовый browser context и постоянный локальный origin. Запуск игры в обычном профиле может изменить его настройки и рекорды. Не копируйте пользовательский профиль и не очищайте storage для обхода ошибки.

## Порядок одной задачи

1. **Цель:** запишите наблюдаемое поведение, которое требуется получить. Для визуальной правки определите нужные игровые кадры; для механики - событие, вход и ожидаемый результат.
2. **Факты:** прочитайте AGENTS, маршрут из CODE_MAP, owner, вызовы и ближайшие tests. Проверьте существующие изменения. Если есть `.git`, используйте `git status --short`, `git diff --check` и scoped diff; для ZIP-копии без `.git` до записи сохраните затрагиваемые исходники вне изменяемых папок, после — сравните содержимое и хеши (PowerShell `Get-FileHash`), не запускайте `git diff --check` без репозитория и не создавайте `.git` только ради проверки.
3. **Гипотеза:** при баге определите этап сбоя. Например, неверное решение AI и верное решение с неверным созданием снаряда требуют разных исправлений. Найдите различающую проверку до записи кода.
4. **Реализация:** меняйте доказанного владельца и необходимые вызовы. Не добавляйте dependency, debug API или новую систему тестов, если задачу решает существующий механизм. Сохраняйте несвязанные изменения.
5. **Проверки:** выполните проверки затронутой границы из VERIFICATION. Для stateful-поведения пройдите одну-две рискованные последовательности, например пауза → fullscreen → продолжение или подбор → рестарт → повторный подбор.
6. **Завершение:** проверьте diff, связанные документы и один CHANGELOG-блок. Сообщите фактические результаты и непроверенные границы. Не превращайте план проверки в утверждение об успешном тесте.

При небольшой понятной задаче достаточно этого маршрута без отдельного плана или набора формальных ролей. Вопрос нужен, когда решение меняет согласованный игровой процесс, данные, внешние действия или объём задачи; обычные обратимые детали решайте самостоятельно.

## Типовые расширения

### Мобильный кокпит и сенсорный ввод

Мобильные переопределения HUD редактируйте в [mobile-cockpit.css](../assets/mobile-cockpit.css), который подключается после `hud.css`; общие стили не дублируйте. Разметка и доступные названия `[data-touch]` живут в `index.html`; ввод, `touchPointers`, pointer capture, `clearInputs` и сброс при изменении ориентации — в `runtime.js`. Сохраняйте `touch-action:none` именно на кнопках, `pointercancel`/`lostpointercapture`, `blur`/паузу и поддержку двух независимых пальцев. Поворот отменяет старые касания, но обычное изменение высоты окна от браузерной панели не должно прерывать управление. Не меняйте gameplay-правила в CSS/DOM.

Отступы от вырезов телефона используют `env(safe-area-inset-*)`, высота страницы — `100dvh` после fallback `100vh`; не отключайте pinch-zoom. При изменении размеров кнопок проверяйте, что каждая зона нажатия >=44×44 CSS px, нет наложений на мини-карту, спидометр, круг, секторы и инструктаж. Точка входа: `node tests/browser-smoke.mjs --mobile` (5 размеров, mobile:true и имитация касаний); полный браузерный прогон — по [VERIFICATION.md](VERIFICATION.md). Настоящие вырезы, физическое multitouch, iOS/Safari и производительность GPU нуждаются в ручной проверке.

### Новый модуль или выделение логики из runtime

Сначала определите входы, выходы и владельца side effects. Для чистых вычислений используйте plain-data API по образцу `opponent-brain.js` или `ballistics.js`; существующие модули с Node tests экспортируют API через `module.exports` и регистрируют его в `CyberRace`.

Если новый файл должен исполняться в браузере, добавьте `<script>` перед потребителем в `index.html`; согласуйте `required` и `orderedScripts` в structural validator. Node tests не зависят от браузерного порядка scripts и сами по себе не обнаружат пропущенное подключение. Обновите CODE_MAP и bootstrap в архитектуре. При обычном выделении сохраните поведение, порядок вычислений и потребление RNG.

### Интерактивные подсказки в игре

Используйте [pilot-tutorial.js](../src/game/pilot-tutorial.js) как чистую конечную машину: события перехода получают от успешных игровых владельцев (`updatePlayer` после фактического изменения скорости, `fireGun` после выстрела, `activateNitro` после списания заряда). Нельзя засчитывать простое нажатие клавиши, не приведшее к действию. Подсказка защиты начинается после обнаружения приближающейся ракеты в штатном `updateProjectiles` и только при готовом импульсе. Для паузы используйте `player.totalTime` и `canControl`, не добавляйте независимые `setTimeout` или новые награды. `renderPilotTutorial` изменяет только DOM; `src/game/pilot-tutorial.js` не зависит от окна, renderer или localStorage. Редактируя шаги, синхронизируйте клавиатуру/сенсор/standard gamepad, тексты меню, компактный HUD и тесты `tests/pilot-tutorial.mjs` / `tests/browser-smoke.mjs`. Для изменённой семантики сохранения проверяйте старые объекты настроек без новых полей.

### Боевые сигналы и рестарт без потери заезда

Выбирайте владельца по [карте кода](CODE_MAP.md): вычисление стороны угрозы и её приоритета — чистые функции [threat-feedback.js](../src/ui/threat-feedback.js) в `CyberRace.ui`; обнаружение ракеты — `updateProjectiles`, источник нанесённого урона — `applyPlayerDamage`; визуальная разметка — `index.html` и `assets/hud.css`. Не переносите урон в UI и не добавляйте чтение DOM в чистый модуль. Во время паузы и вне игры сигнал должен быть скрыт; таймер урона использует `player.totalTime`, а не `Date.now`. В низком качестве и при `prefers-reduced-motion` остаются значимые цвет и текст без навязчивой анимации. Изменяя направление, прогоните `node tests/threat-feedback.mjs` и браузерную раскладку: враг и машина могут ехать с любым heading.

Кнопка рестарта в паузе и физическая клавиша R должны вызывать `requestRaceRestart`, а не внутренний `window.restartGame`. Диалог `#restart-confirm` остаётся отдельным от `#pause-menu`: отмена из движения возобновляет гонку, а из паузы оставляет на паузе; подтверждение только после явного действия вызывает старый рестарт. Вызовы из начала игры, окончания гонки и внутренние тестовые входы остаются без дополнительного подтверждения. Проверяйте R/Shift+Tab/Escape и контроллер Start с открытой модалкой, отсутствие срабатывания оружия и сохранность checkpoint. Не изменяйте ключи `localStorage`.

### Тайминг секторов без изменения гонки

Измерения принадлежат [sector-timing.js](../src/game/sector-timing.js): `createSectorTimer`, `observe` для пересечения 1/3 и 2/3, `closeLap` для третьего сектора, `snapshot` для HUD/финиша. Runtime лишь передаёт `lap`, `t`, игровое `curLap` и признаки допустимого движения. Не вызывайте `closeLap` на основании одного перепрыгивания координаты: только после существующей проверки пересечения стартовой линии в `updatePlayer`. При death/respawn — `invalidate`; при restart и смене маршрута — `reset`; при checkpoint restore — `resume`, что исключает текущий неполный круг без изменения схемы сохранения. Данные секторов не приносят награды; только факт успешного полного замера (`lastCompleted.lap`) разрешает `resolveLapCompletion(validLap)` обновить лучший круг. Даже при невалидном времени переход круга и кредиты сохраняют прежние правила.

Для правки запустите `node tests/sector-timing.mjs`, связанные `tests/garage.mjs`, `tests/championship.mjs`, `tests/approved-features.mjs` и браузерный smoke. Новый HUD расположен над временем круга, на узких экранах — слева ниже контракта; проверяйте совместно с оружием, мини-картой и серией обгонов, включая 360×460. Временные сообщения следует показывать по `player.totalTime`, а не через дополнительные таймеры браузера.

### Призрак лучшего круга

Для новой задачи начните с [lap-ghost.js](../src/game/lap-ghost.js): чистый `createLapGhostTracker()` управляет буфером и временем, `createLapGhostVisual({THREE,scene})` — только сценой. Не записывайте позиции прямо в `runtime.js`, не вводите второй источник времени или RNG и не сохраняйте путь в localStorage. Графика призрака не должна участвовать в коллизиях, AI или оружии и не должна забирать геометрию/материалы у `createCarFactory`.

Runtime вызывает `beginLap` в начале и после круга, `record` после вычисления позиции, `completeLap` только при валидированном пересечении, `invalidate` при смерти/возврате, `reset` при рестарте, смене маршрута, меню и checkpoint restore. В последнем случае первый неполный круг нельзя считать корректным; запись начинается после ближайшего завершённого круга. При подключении нового файла обновите последовательность scripts и структурный валидатор; для настройки используют существующий `cyberRaceSettings.lapGhost` с обратной совместимостью. Проверяйте `node tests/lap-ghost.mjs`, `node tests/sector-timing.mjs`, `node tests/garage.mjs`, `node tests/browser-smoke.mjs` и реальную смену best/invalid при движении за рулём. В low quality контуры должны отключаться, при паузе и финише модель должна скрываться.

### Плавный газ, тормоз и управление геймпадом

Нормализация стандартного геймпада и объединение устройств принадлежат [control-input.js](../src/game/control-input.js): `readStandardGamepad(pad)` и `resolveDrivingInput(keys,touch,pad,enabled)`. Изменять сопоставление RT/LT, крестовины и мёртвой зоны нужно здесь, а не в `pollGamepad` или `updatePlayer`. Runtime владеет настоящим `navigator.getGamepads()`, событиями Start/A/B и паузой. [player-driving.js](../src/game/player-driving.js) принимает доли газа/тормоза 0–1, сохраняя совместимость с bool для цифровых кнопок; не меняйте 120-Hz подшаги и торможение до нуля ради одной карты ввода.

Для проверки запустите `node tests/contracts.mjs` (0/25/50/100%, цифровой fallback, отключение, кривые торможения и 30/60/144 FPS), затем `node tests/browser-smoke.mjs --approved` (реальный Chrome с синтетическим стандартным геймпадом, частичный газ/тормоз, меню и сенсор). Для физического устройства дополнительно проверьте плавное нажатие RT/LT, нейтральное положение стика, крестовину, отключение во время заезда и продолжение после паузы. Синтетический тест не заменяет аппаратную проверку.

### Новый формат одиночной гонки

Открывайте [config.js](../src/game/config.js), поле `SINGLE_RACE_MODES`: оно задаёт круги, версию рекордов и награду за круг/победу. Следом проверяйте `singleRaceMode`, `raceLaps`, `selectSingleRaceMode`, `syncRaceModeUI`, `saveRecords`, `completeLap` и `finishGame` в [runtime.js](../src/game/runtime.js). Вёрстка выбора — `index.html`, оформление — `assets/menu.css`. Хранилище остаётся `cyberRaceTrackRecordsV1` с отдельным `recordVersion` для каждого формата: не меняйте старую версию классики и не очищайте данные игрока.

Новая длина обязана проходить через `raceLaps()` как для игрока, так и для AI, HUD, рестарта, таблицы рекордов и финиша; чемпионат всегда должен брать свои этапы 3/4/5. Значения наград должны поддерживаться `createTuningStore.award`, при этом повторный финиш не должен выдавать деньги заново. Проверяйте `node tests/garage.mjs` и `node tests/browser-smoke.mjs` плюс полный набор перед выпуском. Реальная управляемость на всю дистанцию требует отдельной ручной проверки.

### Новый бонус или изменение существующего

В `pickup-model.js` находятся `data`, набор типов и шаблоны geometry. Эффект игрока задаёт `checkBonuses`, эффект AI - отдельная ветка `updateOpponents`. Изменение одной ветки не изменяет другую автоматически.

Проверьте появление через `spawnBonus` и `spawnBonusAt`, лимиты, удаление через `removeBonusAt` и таймер повторного появления. Общие ресурсы принадлежат фабрике. Проверьте новый и прежние типы в игре, подбор обоими участниками, reduced motion и повторный старт. Атлас PNG не является источником текущих 3D-моделей. Существующие Node tests не доказывают ни внешний вид, ни эффекты подбора.

### Оружие, попадания и боевой баланс

Разделяйте выбор цели/траекторию, создание mesh и применение урона. Чистая математика находится в `src/weapons`, решение AI - в `planOpponentAttack`, runtime владеет боезапасом, projectile pools, звуком, shields и damage.

Для бага вычислений добавьте проверку в ближайший существующий набор. Для нового поведения проверьте расход боезапаса, попадание и промах, смерть/потерю цели, владельца снаряда, shield/invincibility, лимит и повторное использование снарядов. Пулемёт, ракеты игрока и атака AI используют разные runtime-ветки; правка одной не доказывает исправность остальных.

### Настройка или изменение постоянных данных

Значения по умолчанию принадлежат `SETTINGS_DEFAULTS` в `config.js`; допустимые значения нормализует runtime после загрузки. Оба меню используют элементы `[data-setting]`, синхронизацию `syncSettingsUI` и общий change-handler.

Для новой настройки проверьте default, чтение прежнего объекта без нового поля, валидацию, оба меню, сохранение и действие без перезапуска страницы, если это требуется задачей. У `storage.js` нет системы schema migration. Изменение ключа или смысла рекорда требует отдельного решения о совместимости; не выдавайте очистку storage за миграцию.

### Машины, бонусы, HUD и эффекты

Сохраняйте интерфейс модели, ориентацию осей, крепления оружия и независимо анимируемые колёса из ARCHITECTURE. Проверяйте реальный игровой кадр с камерой и HUD, а не только отдельную модель или PNG. Для бонусов различайте семь силуэтов и текущую подачу без плашек над предметами.

Не помещайте создание geometry, material, canvas texture или отдельного источника света в повторяющийся кадр без обоснования. `mergeModelMeshes` предназначен для фиксированных прямых mesh-детей; анимируемые группы остаются отдельными. Сравнивайте вид и производительность на одинаковых настройках, учитывайте reduced motion, рестарт и жизнь общих ресурсов.

## Как локализовать проблему

| Наблюдение | Первый различающий check |
|---|---|
| Нет стартового экрана или boot не ready | Console/Network: порядок локальных scripts, доступность CDN, ошибка до или после `loadThree` |
| Тест математики проходит, но попадание неверное | Сопоставить входы чистой функции и применение результата в `updateProjectiles`; отдельно проверить damage/mesh |
| После меню машина едет или стреляет сама | Проверить `clearInputs`, menu/input guards и последовательность pointer → focus → closeMenu; воспроизвести blur/fullscreen |
| После подбора пропадают другие бонусы | Проверить общие geometry/material и путь `removeBonusAt` → `disposeObject3D`; сравнить до/после рестарта |
| В другом адресе нет рекордов | Сначала сравнить origin: scheme, host и port. Не переименовывать storage keys |
| Покупка или кредиты пропали после второй вкладки | Сравнить `cyberRaceTuning` до и после *каждой* записи, `createTuningStore.syncFromStorage` и обработчик `window.storage` в runtime; начать с `tests/garage.mjs`, затем `tests/browser-smoke.mjs`. Чтение перед записью предотвращает последовательные stale overwrites, но не атомарно при одновременной записи |
| Изменились replay-ожидания | Проверить порядок RNG, dt и входные состояния; не перезаписывать expected значениями падающего теста |
| Снижается FPS или растут GPU-ресурсы | Повторить одинаковый сценарий с фиксированным quality; разделить начальный прогрев pools, постоянный рост и смену auto-quality |

Это маршруты исследования, а не готовые диагнозы. Фактическую причину подтверждайте воспроизведением или различающим check; неизвестное отмечайте явно.

## Как вести CHANGELOG.md

CHANGELOG — **история изменений игры для игроков**, а не журнал работы разработчика или отчёт о тестах.

1. Новые записи добавляйте **сверху**, с датой фактической правки. Если за одну проходку выполнено несколько связанных изменений, объедините их в один раздел.
2. Пишите простыми словами от лица игрока: **«Добавлено»**, **«Исправлено»**, **«Улучшено»**. Укажите, что конкретно изменилось и чем это полезно. Не перечисляйте намерения, предложения, неподтверждённые баги или планы.
3. Для каждого пункта проверяйте фактическое изменение в исходниках или интерфейсе. Если поменяли только тесты или документацию, **не называйте это новым игровым функционалом**. Информацию о командах, логах, хешах и статусах тестирования помещайте в отчёт о работе, а не в обычный CHANGELOG.
4. Не включайте в записи пути к локальным дискам, идентификаторы резервных копий, детали внутреннего процесса, сырые стеки ошибок и многочисленные технические сокращения. При необходимости технические детали находятся в [архитектуре](ARCHITECTURE.md) и [проверках](VERIFICATION.md).
5. Сохраняйте последовательность дат и реальные исторические изменения, но объединяйте старые дубли и громоздкие технические заметки в понятные формулировки. Не выдавайте ранее исправленную проблему за новое исправление.
6. После завершения работы перечитайте новый раздел и сопоставьте его с фактическим списком изменённых файлов. Пункты о неизменённых возможностях не добавляйте.

Пример: «**Исправлено:** при повреждении сохранения чемпионата этап запускается заново с предупреждением, а результаты завершённых этапов остаются на месте».

Содержимое кода и scripts определяет текущее поведение. План или прежний CHANGELOG не доказывает, что оно сохранилось. Не копируйте весь набор констант или текущие результаты тестового запуска в несколько документов.
